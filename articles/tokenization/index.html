为什么 LLM 不按字或单词阅读？从 Tokenization 的取舍说起

从词表条目与 Token 数的区别出发，通过 BPE 和 SentencePiece 实验理解子词切分的收益、边界与代价。

我们写程序时，很容易把“文本切分”理解为一个字符串操作：按空格拆成单词，或者遍历字符数组。

但如果让你为一个语言模型设计输入格式，会很快遇到麻烦。假设用户发送了：

我喜欢 Swift programming

应该把它拆成几个单位？按汉字、英文单词、字符，还是干脆按 UTF-8 字节？这些选择看上去只是拆分方式不同，却会影响模型能够处理哪些文字、每句话有多长，以及计算时要付出什么代价。

在上一篇文章里，我们知道了模型会先把输入文字转换为 Token ID。但那篇文章没有回答一个更基础的问题：为什么要把文字切成这样的单位，而不是直接按字或完整单词处理？

这次我们从头设计一套切分方案，看看问题究竟出在哪里。

一、先分清两个容易混淆的数字

假设我们现在只有三个可识别的片段：

pro、gram、ming

把这三个片段放在一张表里，给每个片段分配不同的编号，它们就构成一个最简单的玩具词表。

当输入 programming 时，我们可以把它表示成：

pro | gram | ming

此时有两个数字：

  • 词表大小是 3：词表总共有三种不同的条目。
  • 这段文本的 Token 数是 3：编码 programming 用到了三个条目。

现在，我们希望这个常见单词只用一个 Token 表示。方法是将 programming 也加入词表。原有的 pro、gram、ming 仍然保留，因为它们可能用于其他文本。

原来的玩具词表 扩充后的玩具词表
可用条目 pro、gram、ming pro、gram、ming、programming
词表大小 3 4
编码 programming 的 Token 数 3 1

增加词表条目，可能减少某段文本的 Token 数。 这两个数量恰好朝相反方向变化。

它们也是后面所有取舍的起点：词表是模型需要维护的“可用单位全集”，而一段文本的 Token 数是这次处理实际用到的单位个数。不能因为一句话只切成一个 Token，就认为词表里只需要存一个条目。

图 01：玩具词表示意：词表从 3 条目增加到 4 条目，programming 的编码结果从 3 个 Token 变为 1 个。并非真实模型的 Token ID。

二、那为什么不把所有单词都放进词表？

直接按单词切分有个明显的好处：常见英文单词可能只需要一个 Token。

但问题是，什么才算一个单词，以及词表能不能事先收录所有可能的单词？

以开发中的函数名为例：

fetchUserProfileAsync

它不是自然语言词典里必然存在的单词，但程序随时可能创造这样的标识符。英文的词形变化、拼写错误、专有名词，以及不依靠空格分词的中文，也会让“列出所有完整单词”的方案越来越难维持。

如果词表里没有完整的 fetchUserProfileAsync，模型是不是就没法表示它了？

不一定。只要有适当的小片段，仍然可以把它拆成多个已知单位。比如一种假设的切分方式是：

fetch | User | Profile | Async

这个例子只是说明“可以用已有片段拼接”，不是对任何具体模型的实际编码结果。

于是，我们希望词表既保留一些足够小、便于组合的基本单位，又收录一部分高频的长片段。

但选哪些长片段比较划算？

三、BPE：让高频片段逐步变成新单位

一种常见方法是 BPE（Byte Pair Encoding）。它的核心直觉可以先用字符级的玩具语料来理解：反复寻找当前最常见的相邻片段组合，把它们合并为一个新片段。

假设训练语料只有四个单词：

low
lower
lowest
low

先按字母拆开：

l | o | w
l | o | w | e | r
l | o | w | e | s | t
l | o | w

这里的“相邻”很具体：在 low 中，l+o 和 o+w 相邻，l+w 却不相邻，因为中间隔着 o。

再统计整个语料中出现了多少次：

相邻组合 次数
l + o 4
o + w 4
w + e 2
e + r 1
e + s 1
s + t 1

low 在语料中重复出现两次，所以它的相邻组合也要计数两次。

最高频次出现了并列。为了演示，我们规定先合并 l+o，于是整个语料变成：

lo | w
lo | w | e | r
lo | w | e | s | t
lo | w

这时，lo 已经是下一轮统计中的一个单位了。重新统计，相邻组合 lo+w 出现四次，于是可以继续合并：

low
low | e | r
low | e | s | t
low

经过两轮，原来需要三个字母单位的 low，现在只需要一个。与直接把所有可能单词收进词表不同，这种方法使用语料里反复出现的组合，逐步决定哪些更长片段值得加入。

为什么要看频率？在这个简化例子中，合并出现四次的片段组合，会让训练语料中的片段总数减少四个；合并只出现一次的组合，只能减少一个。同样新增一个词表条目，高频合并通常能在当前语料中节省更多编码位置。

不过真实 Tokenizer 并不一定从 Unicode 字符开始做 BPE，也可能涉及字节、预切分或其他规则。上面的四个单词只用来展示合并机制，不能当作 o200k_base 或其他生产 Tokenizer 的训练记录。

图 02：字符级 BPE 教学示例。l+o 与 o+w 最初均出现 4 次；先按约定合并 l+o，再合并 lo+w。

四、真实实验：词表翻倍，Token 数会减半吗？

接下来我们不只靠推理，而是运行一组小实验。

使用 SentencePiece 0.2.1，在同一份包含中英文和 Swift 示例的玩具语料上分别训练词表大小为 128 和 256 的 BPE Tokenizer。训练语料有 12 条不同样本，重复 40 遍，共 480 行；它很小且刻意重复，适合检验机制，却不能代表 GPT 等生产模型的训练数据。

以下是实验记录中的实际结果：

输入文本 128 词表 256 词表
我喜欢 Swift programming 6 3
Hello, world! 14 4
func fetchUser() async throws 11 5
fetchUserProfileAsync 4 2
programming 1 1
我喜欢编程 😀 8 3

对我们一开始那句 我喜欢 Swift programming，实际切分分别是：

128 词表：
▁ | 我 | 喜 | 欢 | ▁Swift | ▁programming

256 词表：
▁我喜欢 | ▁Swift | ▁programming

▁ 是 SentencePiece 用来表示空格边界的可见记号。这个对照告诉我们，在较大的词表里，我喜欢 已经可以作为更长的片段出现。

再看函数名：

128 词表：
▁fetchUser | Profile | A | sync

256 词表：
▁fetchUser | ProfileAsync

较大的词表收录了 ProfileAsync 这样的组合，因此减少了片段数。

但是，programming 在两套词表里都只占一个 Token：它已经无法从一个 Token 再缩短成“半个 Token”。词表扩大，收益并不会平均分配给每段文本。

实验里的六条文本都通过了编码后再解码等于原文的检查。可复现代码见SentencePiece 对照脚本。

需要强调的是：这里测到的是两套自训练 SentencePiece BPE 的切分结果，不是 GPT 的切分，也没有测量推理速度或 API 账单。

图 03：由同一玩具训练语料得到的 SentencePiece BPE 128 / 256 词表实测。▁ 表示空格边界，并非下划线。仅代表本实验，不等于 GPT 的实际切分。

五、既然大词表可以减少 Token，为什么不继续扩大？

看到这里，你可能会有一个疑问：

既然把更多常见片段加入词表，就能让同一段文字使用更少的 Token，那为什么不干脆把词表做得更大一些？

比如，把常见的英文单词、中文词组，甚至经常出现的代码片段都收进去。这样模型每次需要处理的 Token 不就更少了吗？

这个思路确实有道理，但我们忽略了一件事：词表并不只在切分文本时使用，它还会影响模型如何接收输入，以及如何生成输出。

词表越大，这两个环节的代价也会发生变化，只是变化的方式并不一样。

图 04：128 / 256 词表的 6→3、1→1 来自自训练 SentencePiece 0.2.1 玩具实验。输入端侧重 Embedding 参数与存储，输出端侧重标准完整词表输出层的单步计算；未测量真实 GPT 的切分与推理延迟。四张配图已由作者于 2026-10-30 确认；尚未公开发布。

输入端：词表越大，需要保存的向量越多

我们在上一篇文章里提到过，文字经过 Tokenizer 之后，会变成一串 Token ID。

但 ID 本身只是编号，模型不能直接从编号中理解文字。因此，模型需要通过 Embedding，把每个 Token ID 转换成一个可学习的向量。

你可以暂时把它理解为一张很大的表：每个 Token 对应其中的一行数字。

现在假设词表有 5 万个 Token，每个 Token 对应一个 4096 维的向量。

那么这张表需要保存多少个数字？

50,000 × 4,096 = 204,800,000

也就是大约 2 亿个参数。

如果我们觉得 5 万还不够，把词表扩大到 50 万，而向量维度保持不变，这张表的参数量也会增加到原来的十倍。

按每个参数占用 2 字节的 FP16 格式估算，仅这张 Embedding 表，就会从约 410 MB 增加到约 4.1 GB。

但这里有个容易误解的地方。

表变大，不代表每次查找一个 Token 时，都要把整张表计算一遍。

就像通过数组下标找到某个元素，我们只需要找到对应的那一行向量，而不是遍历所有 Token。

因此，词表变大给输入端带来的主要代价，是需要保存更多参数，占用更多存储和内存，而不是输入查表的计算量也跟着增加十倍。

输出端：词表越大，每次生成时要考虑的候选越多

到了模型生成文字的时候，情况就不一样了。

假设模型已经处理完上下文，准备生成下一个 Token。

它需要解决的问题是：接下来应该输出词表里的哪一个 Token？

在典型的语言模型中，输出层会为词表中的候选 Token 计算分数，再根据这些分数决定下一步输出什么。

如果词表有 5 万个条目，输出层通常需要产生 5 万个候选分数。

如果词表扩大到 50 万个条目，需要考虑的候选也就增加到了 50 万个。

这与输入时根据 ID 查找一个向量不同。

输入端主要增加的是需要保存的参数；而输出端在常见的完整词表计算方式下，还会增加每一步的计算量。

当然，这不意味着整个模型的推理速度一定会降低十倍。输出层只是模型计算的一部分，实际实现中也存在权重共享和其他优化方式。

那么，减少 Token 带来的收益呢？

我们再回头看看前面的实验。

我喜欢 Swift programming 在 128 词表下需要 6 个 Token，扩大到 256 词表后，只需要 3 个。

这意味着，模型处理这段文本时，需要面对的序列变短了。

如果是在逐 Token 生成的过程中，能够用更少的 Token 表达相同内容，也就可能减少生成轮次。

但另一段文本 programming，在两套词表中都只占 1 个 Token。

它已经不可能再缩短成半个 Token 了。

所以，随着词表不断扩大，我们并不能保证每次新增条目都能带来同样的收益。

这就形成了一个有意思的取舍：

词表越大，可能让模型用更少的 Token 处理文本；但与此同时，模型需要保存更多参数，生成每个 Token 时也可能付出更高的计算代价。

至于哪一种词表规模更合适，就需要结合实际语料、模型结构以及运行环境来判断，而不能只根据词表大小下结论。

我们前面的 SentencePiece 实验验证了 Token 数量的变化，但还没有测量真实模型的推理速度。因此，目前只能确认这两种相互制约的因素，不能直接算出最优词表大小。

六、那干脆所有文字都按 UTF-8 字节切分呢？

还有一个更彻底的方案：不把常见词组合作为大 Token，直接把文本编码成 UTF-8 字节，每个字节作为一个单位。

这很容易获得广泛覆盖：单个字节有 256 种可能值，任何合法 UTF-8 文本都能够表示为字节序列。

但字节数和人眼看到的字符数不同：

文本 Unicode 码点数量 UTF-8 字节数
A 1 1
中 1 3
😀 1 4
👨‍👩‍👧‍👦 7 25

比如汉字 中 的 UTF-8 字节是 E4 B8 AD。如果每个字节占一个 Token，它就需要三个 Token；但在能把这三个字节合并成一个词表条目的字节级 BPE 中，最终也可能只需要一个 Token。

注意：Unicode 码点数量不一定等于人眼看到的字符数量，上表最后一行就是由多个码点组成的一个可见 Emoji。

纯字节切分的词表虽然小，但常见单词、中文和 Emoji 往往会产生更长序列。对于自回归语言模型，输出更多 Token 意味着需要更多生成轮次。每轮输出层可能便宜，却未必能抵消额外的模型计算。

反过来，如果一个 Tokenizer 只依赖收录的完整字符或片段，而没有合适的字节级覆盖机制，那么遇到词表外的字符时可能需要使用 <unk>，无法完整保留原文。这取决于具体实现，不能说所有 Tokenizer 都天然支持任意文本无损往返。

由此我们能看出常见子词/字节级方案的吸引力：以较小的基础单位覆盖未知文本，同时将高频片段合并成较长 Token，避免总是付出纯字节序列的长度代价。

回到最初的问题

最开始，我们只是想处理一句 我喜欢 Swift programming。现在再看 Tokenization，它就不只是“把字符串拆开”这么简单。

如果只收录完整单词，词表难以覆盖不断出现的新词和代码标识符；如果只保留极小的字符或字节单位，序列又可能变得很长。BPE 等子词方法尝试在这两端找到折中：让常见组合使用较短的序列，又保留表示陌生输入的能力。

这也解释了一个经常被忽略的事实：

一段文字有多少字、多少单词，并不能直接告诉我们它会占用多少 Token。 实际数字由具体 Tokenizer、词表和编码规则决定。应用向模型 API 发送的消息还可能包含其他封装和特殊标记，单独对正文运行 encode 也不等于最终计费 Token 数。

不过，我们解决的是“怎样把文本转换成有限词表中的编号”，还没有解释另一个问题：一个 Token ID 只是编号，为什么模型通过这些编号就能学会预测有意义的文本？

这个问题需要从模型参数怎样学习开始，再回头理解 Token ID 如何变成向量。
