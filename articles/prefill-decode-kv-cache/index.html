GPT 如何避免重复计算？从 Prefill 到 KV Cache

从 Prefill 建立历史 K/V 到 Decode 增量处理新 Token，解释因果 Attention 为什么允许复用旧结果，以及 KV Cache 的显存代价。

先说结论：KV Cache 让 GPT 在生成新 Token 时复用历史计算结果，而不必每一轮都重新处理整个前缀。 之所以可以复用，是因为因果遮罩保证旧位置看不到未来 Token；追加新 Token，不会改变旧位置在各层已经算出的表示。

它换来的不是“免费加速”：历史 K/V 需要占用显存，而且上下文越长、同时处理的请求越多，占用就越大。

下面沿着一次生成过程回答三个问题：Prefill 怎样建立缓存？为什么旧结果仍然有效？缓存节省计算的代价是什么？

一、一次生成中，Prefill 和 Decode 分别做什么？

假设用户提交的问题被切成四个 Token：A、B、C、D。它们在推理开始时已经全部确定，模型可以一次处理这段已知输入。

这一步叫 Prefill（提示处理）。在 Transformer 的每一层里，A、B、C、D 可以并行计算；因果遮罩仍然限制每个位置只能读取自己和前面的位置：

位置 可以读取
A A
B A、B
C A、B、C
D A、B、C、D

因此，并行处理不等于让 A 看到 B、C、D。并行发生在同一层的位置计算之间；网络仍然要一层接一层地传递结果。

Prefill 结束时有两个结果：

  1. 模型根据最后一个输入位置 D 的输出，计算下一个 Token 的概率分布，并选出 E。
  2. 模型把各层为 A、B、C、D 算出的 K 和 V 保存起来，作为初始 KV Cache。

注意：此时缓存里还没有 E。E 只是刚刚选出的预测结果，尚未作为输入经过 Transformer。

接下来进入 Decode（逐 Token 生成）。模型把 E 作为新输入，计算 E 自己的 Q、K、V；E 的 Query 读取缓存中 A～D 的 K/V，同时把 E 的 K/V 加入缓存，再根据新的输出选出 F。

阶段 本轮输入 本轮结束后的缓存 选出的下一个 Token
Prefill A、B、C、D A～D 的 K/V E
Decode 第一轮 E A～E 的 K/V F
Decode 第二轮 F A～F 的 K/V G

Prefill 为已知 Prompt 建立各层 K/V；Decode 用新 Token 的 Q 读取历史 K/V，并将新 K/V 留给后续生成。

这就是从 Prefill 到 Decode 的交接：Prefill 一次处理已经知道的 Prompt；Decode 每轮只处理新确定的 Token，并读取此前保存的历史 K/V。

Prefill 和 Decode 都是推理阶段内部的两个阶段，不是训练与推理的对应关系。常规模型训练也可以在因果遮罩下并行处理已知序列，但训练还需要计算损失并通过反向传播更新参数。

二、如果没有 KV Cache，会重复做多少工作？

先看一种可行但低效的做法：每生成一个 Token，就把“原始 Prompt + 已生成内容”重新送进模型，完整计算一遍。

仍然从 A、B、C、D 四个位置开始。假设接下来依次选出 E、F、G，那么模型要处理的前缀长度是 4、5、6、7：

计算轮次 本轮前缀长度 不使用缓存：重新处理 使用缓存：本轮新增处理
Prefill，预测 E 4 4 个位置 4 个位置
Decode，预测 F 5 5 个位置 1 个位置
Decode，预测 G 6 6 个位置 1 个位置
Decode，预测 H 7 7 个位置 1 个位置
累计 — 22 个位置 7 个位置

不使用缓存时，前面的位置会反复计算；使用缓存时，四个初始位置只在 Prefill 中处理一次，后面每轮只新增一个位置。

这张表数的是每层处理过的位置数量，用来展示重复工作；它不是 FLOPs 或真实速度的测量。要理解为什么这 15 个位置可以省掉，还需要回答一个关键问题：新 Token 到来后，为什么旧 Token 的计算结果不会改变？

三、为什么追加新 Token，不需要重算旧 Token？

关键在于 Attention 不是两个 Token 对称地互相计算。每个位置用自己的 Query（Q）查询允许访问的 Key（K），再按匹配结果读取对应的 Value（V）。

假设现在有五个位置 A、B、C、D、E。下面每一行表示谁在发起查询，每一列表示它可以读取谁的 K/V：

Query \ Key / Value A B C D E
A 的 Query ✓ — — — —
B 的 Query ✓ ✓ — — —
C 的 Query ✓ ✓ ✓ — —
D 的 Query ✓ ✓ ✓ ✓ —
E 的 Query ✓ ✓ ✓ ✓ ✓

✓ 表示允许读取；— 表示因果遮罩禁止读取。

从表中可以直接看到两个方向：

  • A、B、C、D 的 Query 都不会读取 E，因为 E 是它们的未来位置。
  • E 的 Query 可以读取 A、B、C、D，因为它们是 E 的历史位置。

所以，旧 Token 并不是与 E 毫无关系：E 仍然会使用旧 Token 已经算好的 K/V。只是旧 Token 不会反过来读取 E。

这正是旧结果能够复用的原因。追加 E 之前，A、B、C、D 能看到的信息已经确定；追加 E 之后，它们的可见范围没有变化。因果遮罩会在 Softmax 前屏蔽未来位置对应的注意力分数，使这些位置的注意力权重为 0。

追加 E 只增加新的 Query 行；原有 A～D 的可见范围不变，旧 Query 对 E 的位置仍被因果遮罩。

这个性质会逐层延续。在标准 decoder-only Transformer 中，跨 Token 传递信息的是因果 Attention；残差连接、归一化和 FFN 都在各个位置分别处理，不会把 E 的信息传回 A、B、C、D。因此，旧位置在第一层的表示不变，后续层接收到的旧位置输入也不变。在常规关闭 Dropout 的确定性推理中，只要模型参数、已有 Token 和位置没有改变，旧位置各层的表示以及由它们得到的 K/V 就可以继续复用。

还有一个实现边界需要分清：因果语义保证旧 Query 不会读取 E，但不保证每一种底层实现都跳过了对应的乘法。 有些实现可能先算出注意力分数再应用遮罩，优化过的 Kernel 也可能直接跳过部分无效计算。这里讨论的是哪些结果在语义上有效、因此可以复用，而不是断言所有硬件都执行完全相同的指令。

四、为什么缓存 K 和 V，而不是 Q？

现在看新位置 E 要完成什么计算：

  • E 的 Q：决定它要从历史中查询什么。
  • A～D 的 K：供 E 的 Q 计算匹配分数。
  • A～D 的 V：根据匹配权重，提供需要汇总的信息。

历史位置的 Q 已经完成了它们各自的查询。计算 E 的结果时，不需要再拿 A、B、C、D 的旧 Q 查询一遍；但 E 仍然需要它们的 K/V。

因此，推理时缓存的是每一层历史位置的 K 和 V。E 自己的 Q、K、V 则在本轮计算，其中 K/V 会被加入缓存，供后续 Token 使用。

把 E 的这一步简化写出来：

Attention(qE,[KA:D,kE],[VA:D,vE])=softmax(qE[KA:D;kE]⊤dk)[VA:D;vE]\mathrm{Attention}(q_E, [K_{A:D}, k_E], [V_{A:D}, v_E]) =\mathrm{softmax}\left(\frac{q_E [K_{A:D};k_E]^\top}{\sqrt{d_k}}\right)[V_{A:D};v_E]Attention(qE​,[KA:D​,kE​],[VA:D​,vE​])=softmax(dk​​qE​[KA:D​;kE​]⊤​)[VA:D​;vE​]

这里用一个 Attention 头说明计算关系，省略批次和层索引。真实模型会在每个需要缓存的 Attention 层分别保存自己的 K/V。

KV Cache 省掉的是旧位置的重复计算，不是新位置读取历史信息的计算。 E 仍然要用自己的 Q 与历史 K 匹配，并按权重读取历史 V。

五、用实验检查：缓存有没有改变计算结果？

我们用 NumPy 构建了一个简化的双层因果 Attention 网络，对比两条路径：

  • 全量重算：每次追加 Token，都重新计算整个前缀。
  • KV Cache：第一次处理完整 Prompt；之后每次只计算新位置，并复用每一层已经保存的 K/V。

实验固定模型参数和输入，从 4 个位置开始，依次追加三个预先指定的 Token。使用预先指定的 Token，是为了让两条路径处理完全相同的输入；这项实验验证缓存计算是否等价，不测试模型生成质量。

六、省掉重复计算，为什么还会增加显存压力？

因为模型要复用历史 K/V，就必须把它们保存下来。缓存越长，占用越大；同时处理的请求越多，总占用也越大。

在不考虑内存对齐、预分配和其他运行时开销时，KV Cache 的容量可以粗略估算为：

MKV=2×L×B×T×HKV×Dhead×sM_{KV}=2\times L\times B\times T\times H_{KV}\times D_{head}\times sMKV​=2×L×B×T×HKV​×Dhead​×s

其中：

  • 2：分别保存 K 和 V。
  • L：Attention 层数。
  • B：同时处理的请求数量（Batch）。
  • T：每个请求缓存的 Token 数量。
  • H_KV：每层的 KV Head 数量。
  • D_head：每个 Head 的维度。
  • s：每个数值占用的字节数。

例如，假设模型有 32 层、8 个 KV Head、每个 Head 维度为 128，使用 FP16（每个数值 2 字节），单个请求的上下文长度为 4096：

2×32×1×4096×8×128×2=536,870,912 Bytes=512 MiB2\times32\times1\times4096\times8\times128\times2 =536{,}870{,}912\ \text{Bytes}=512\ \text{MiB}2×32×1×4096×8×128×2=536,870,912 Bytes=512 MiB

同样配置下，如果每个请求都是 4096 个 Token：

同时处理的请求数 KV Cache 总量
1 512 MiB
2 1 GiB
5 2.5 GiB
10 5 GiB

这里假设每个请求的缓存长度相同或接近；如果请求长度不同，应按每个请求实际缓存的 Token 数分别计算。这只是 KV Cache 的理论容量，不包括模型权重、其他中间结果和推理框架预留的显存。它说明了为什么长上下文和高并发会带来显存压力。

还要注意，KV Cache 通常属于正在执行的请求：请求完成后，缓存会被释放或回收到内存池，并不是每多问一次就永久累积一份。多轮对话中，如果服务端把之前的聊天记录重新放进下一轮 Prompt，新的请求仍可能需要 Prefill 这些历史 Token；跨请求复用相同前缀属于 Prefix Caching 等另一类优化，不是这里讨论的请求内 KV Cache。

此外，缓存并没有让 Decode 与上下文长度脱钩。每生成一个新 Token，它的 Q 仍要读取当前有效上下文中的 K/V；上下文越长，需要访问的历史数据通常也越多。因此，KV Cache 是用显存和内存访问，换取避免重复计算的机会，并不意味着上下文越长也能保持相同的生成成本。

回到最初的问题

GPT 不必在每轮生成时重新计算整个前缀，是因为因果遮罩保证了旧位置不会受到未来 Token 影响。Prefill 先处理已知 Prompt 并建立初始缓存；Decode 再用新 Token 的 Q 读取历史 K/V，只计算并保存新位置的 K/V。

KV Cache 减少了重复计算，但把一部分成本转移到了显存和历史数据读取上。

下一步值得研究的是：当上下文变长、并发增加时，Prefill 的首 Token 等待时间、Decode 的逐 Token 速度和 GPU 显存之间，究竟如何相互影响？
