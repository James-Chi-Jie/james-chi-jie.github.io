从一次 LLM API 调用开始：模型究竟怎样生成回答？

从文字输入到 Token、Embedding、Transformer，再到逐 Token 生成，串起一次文本 API 请求的完整信息流。

假设我们在应用里接入了一个大语言模型。用户输入：

为什么天空是蓝色的？

我们的代码可能只有这样几行：

# 伪代码，用来表示普通的文本对话请求，并非某个具体 SDK 的接口
response = llm.chat(
    messages=[{"role": "user", "content": "为什么天空是蓝色的？"}],
    stream=True,
)

接下来，屏幕上开始出现模型的回答。

站在应用开发者的角度，我们似乎只是发起了一次网络请求，然后接收返回的文字。可如果把视线往 API 内部移一点，就会发现几个值得追问的地方：请求里传的是一段中文，模型里的大量计算却是针对数字进行的，文字是怎样进入这些计算的？ 有时我们要等一小段时间才看见第一段输出，之后内容逐渐出现，为什么不是一次性把整段回答交回来？ 即使问题没变，两次回答的措辞也可能不同，模型是怎样决定接下来输出什么的？

答案并不是由一个单独的步骤直接写出来的。一次普通的文本生成请求，会经历输入转换、模型计算和持续生成等环节。沿着数据的变化过程往下看，就能逐渐理解这些环节如何协作。

先看完整过程：一条消息怎样变成回答？

可以先把它理解成这样一条信息流：

图 01：概念总览。输入先被转换为数值表示，模型处理已有上下文后逐步生成，已经产生的文字可以通过 API 交付给应用。图中 Prefill 的标注是教学分区；严格说它指模型对已有上下文的计算，并不包括完整的客户端网络请求。

整条信息流里有两个值得注意的变化：输入文字先被转换成数值，才能进入模型计算；模型每选出一个新的 Token，又会把它放进后续计算的上下文中。我们看到的回答，就是这样逐步形成的。

先从文字进入模型的过程说起。

一、模型接收的是文字，为什么要先做 Tokenization？

应用向 API 发送的，是人可以阅读的字符串。

但在我们讨论的语言模型中，主体计算需要的是数值形式的输入。直接把“天”“空”“蓝”等字形放进矩阵，并不能让神经网络完成接下来的运算。

因此，模型输入端通常会先进行一步转换：把文字表示为一串离散的 Token ID。

这个过程叫作 Tokenization，负责执行转换的组件叫 Tokenizer。

先把 Token 理解成模型所使用的文本单位就够了。它有时可能对应一个字、一个词的一部分，或其他字符片段；不保证一个 Token 就是一个汉字或一个完整的词。

比如，图 02 使用一条英文短句展示一次真实编码中从文字到编号的变化。这里切换为英文，是为了能准确核对每个片段和对应的 ID；它并不意味着中文也要按这样的方式拆分。

图 02：OpenAI Cookbook 中 o200k_base 的示例：tiktoken is great! 可以编码为 [83, 8251, 2488, 382, 2212, 0]。图内的分词片段仅服务于理解切分过程，不同 Tokenizer 的结果可能不同。

如果换回开头的“为什么天空是蓝色的？”，同样会得到一串 Token ID。不过，没有指定具体 Tokenizer，就不能从汉字数量直接推断 Token 数量。

文字变成编号之后，已经可以用一串数字表示输入。但这些编号本身还不能表达词语之间的语义关系。

一个 Token ID 本质上只是词表中的编号。假设两个 Token 的编号恰好是 100 和 101，数字相差 1，并不意味着它们的含义更接近。

如果编号本身没有这样的语义关系，模型接下来到底拿什么进行计算？

二、Token ID 只是编号，模型怎样得到可计算的表示？

可以先借用程序中的一个熟悉操作：查表。

假设我们有一张表，每个 Token ID 都能查到一组数字：

Token ID（示意） 查到的数值向量（示意）
100 [0.2, -0.1, 0.7]
101 [-0.3, 0.5, 0.1]

这些数值是为了说明数据结构而随意设定的，不是任何真实模型学到的参数。

Token ID 决定查哪一行，而查询结果不再是一个孤立的编号，而是一组可以参与后续计算的数字。这样的映射通常称为 Embedding。

图 03：中间展示“用 Token ID 查词嵌入矩阵，得到对应向量”；右侧二维散点图只是把高维关系做成容易理解的示意，并不代表模型内部真的在二维空间中存储意义。示例向量也不是实际模型参数。

只有各个位置对应的向量还不够，模型也需要辨别顺序。“猫追狗”和“狗追猫”包含相同的词，表达的关系却完全不同。不同架构利用位置信息的方式不尽相同，例如有的会在 Attention 内部处理位置关系。

还有一个容易混淆的问题：这些向量是谁写进表里的？

通常，它们属于模型训练过程中学到的参数。在实际的普通推理请求中，模型使用已经训练好的参数来计算，并不会因为用户每问一句话就重新训练一次。参数是怎样在训练中逐步调整的，属于另一段过程；一次普通推理请求使用的是已经学到的参数。

原始文字经过 Token ID，最终变成一组可以参与计算的向量。但有了这些向量，还不足以处理整句话中的关系。

因为每个位置上的表示还需要与上下文中的其他位置发生联系。例如，在“为什么天空是蓝色的？”这个问题里，模型需要综合利用整段输入，而不只是孤立地处理“天空”或“蓝色”。

那么，不同位置的数字表示究竟怎样交换信息？

三、有了向量，模型怎样利用上下文？

到这里，每个输入位置都有了可以参与计算的数值表示。但如果这些位置始终只处理自己的信息，模型仍然很难利用一句话中不同部分的关系。

仍以“为什么天空是蓝色的？”为例，模型需要处理的不是孤立的“天空”和“蓝色”，而是它们共同构成的提问。为了看清其中的困难，不妨换一个关系更容易观察的短句：

小明拿起钥匙，把它放进口袋。

只看“它”这个字，无法知道它指向什么；把前面的“钥匙”放进同一段上下文，才有了理解这句话的线索。这里的汉字和词只是便于阅读的片段，不代表某个 Tokenizer 的实际切分结果。

因此，我们希望一个位置在更新自己的数值表示时，不只使用原先那组数字，还能够利用上下文中其他位置提供的信息。

这就是 Attention（注意力机制） 要做的一类工作。

不过，利用上下文并不是把其他词原样复制到当前位置。模型会根据当前参与计算的表示，计算各个可访问位置的相关权重，再把这些位置提供的数值信息按权重组合起来。不同位置可能贡献不同程度的信息；当前位置因此得到一份融入上下文的新数值表示。

图 04-2：权重为教学示意。以第 6 位“它”为例，在 GPT 类模型的因果注意力中，当前位置只使用第 1～6 位，灰色的第 7～9 位不会参与本次计算。图中画的是数值信息的聚合，而不是直接作出“它必定指钥匙”的判断。

在上面的句子中，“钥匙”可以为“它”所在的位置提供有用线索。但注意力权重不等于模型对代词指向的明确判决，也不能凭一根连线就断言某个注意力头真正理解了指代关系。

Attention 只是 Transformer 中的一部分。经过多层注意力和其他计算，各位置的表示会进一步更新。对于最开始的“为什么天空是蓝色的？”这个问题，模型也会以类似方式利用已有上下文进行计算。

到这里，Transformer 产生的仍然是数值表示，而不是写好的文字答案。下一步才轮到输出层：它怎样利用这些数字，决定接下来生成哪个 Token？

四、模型如何决定下一个 Token？

沿着刚才的流程继续往下走。Transformer 已经把输入中的上下文信息融入数值表示，但它交出的仍然是一组数字。这些数字怎样变成“下一步写什么”的选择？

对于典型的 GPT 类模型，模型会取当前序列最后一个位置经过 Transformer 处理后的表示，交给输出层。输出层利用训练时学到的一组权重，把这组表示转换为词表中各个 Token 对应的分数。这些分数叫作 logits。

那么，这些候选 Token 又是从哪里来的？它们并不是模型临时从问题中挑选出的几个关键词。模型本来就有一套用于编码和输出的 Token 词表，输出层通常会给词表中的每个 Token 计算一个分数。比如，假设词表有 10 万个 Token，模型就会得到一组大约 10 万个分数。不是先找出三个候选，再只对它们打分。

有了这些分数，模型才会按照生成策略决定下一步：可以直接选择得分最高的 Token，也可以将分数转换为概率、限制候选范围，再从中采样。无论哪种方式，模型都不是提前写好整段回答，再一个字一个字显示出来。

回到“为什么天空是蓝色的？”。为了看清“打分”和“选择”的区别，假设模型已经生成了这样一段回答：

天空呈现蓝色，主要是因为太阳光在大气中发生了……

接下来会写什么？我们用“散射 / 反射 / 折射”代表三个容易联想到的续写方向，人为设置得分为 2、1、0，并且暂时只在这三个假设选项之间计算概率：

候选续写内容（示意） 假设的 logits 在三个示意选项内计算的概率（约）
散射 2 66.5%
反射 1 24.5%
折射 0 9.0%

图 05：这里把三个中文词语当作便于阅读的续写方向，并用 Softmax 演示从分数到概率的转换。“散射”不一定是实际词表中的一个独立 Token；这三个百分比只对应人为设定的三项得分，并不是对真实模型整个词表的预测结果。

如果采用贪心选择，这一轮会选择概率最高的示意候选“散射”；如果采用采样，也可能沿着其他方向生成。实际的候选范围和最终选择，还可能受到温度、Top-k、Top-p 等解码设置的影响。

这样，同一个问题有时得到不同措辞，就不难理解了：生成过程未必每一步都选择最高分选项。不同的上下文和服务设置也会影响结果。

还有一点容易混淆：下一个 Token 的概率不等于“这句话真实正确”的概率。 模型的分数用于决定接下来如何生成文字，不能直接当作事实核验的结论。

刚刚只演示了一次选择。完整回答还需要模型继续往下生成。

五、为什么回答是逐步出现的？

关键在于：刚刚选出的内容并不是生成过程的终点。

模型会把新生成的 Token 接到已有上下文之后，再依据扩展后的序列预测下一个 Token。新 Token 一个接一个地产生，直到出现结束标记、达到长度限制，或满足其他停止条件。

例如，把“逐步生成”理解为一段不断增长的回答：

“天空……” → “天空呈现……” → “天空呈现蓝色……” → “天空呈现蓝色，主要是因为……”

这里每个引号里的文字是为了帮助阅读而展示的累计回答片段，并不是对真实 Token 切分的逐步实测。

这称为自回归生成：生成下一步时，利用已经存在的前缀；而尚未生成的后续内容，此刻并不知道。对于这里讨论的 GPT 类模型，这也解释了为什么注意力计算要采用因果约束：一个位置可以利用自己以及前面的位置，却不能提前使用后面尚不应看到的信息。

为什么第一段回答有时要等一会儿？

回到开头那次 API 调用，我们常会遇到这样的体验：请求发出后先等待片刻，随后文字才持续出现。之所以会有这种差异，是因为模型推理通常包含两类不同的计算工作：

Prefill（处理已有上下文）：模型先处理请求中已经知道的输入，包括系统提供的上下文、历史消息以及本次提问。对于典型的 Transformer 推理，这些已知位置可以在一次阶段中批量参与计算，并用于形成首次预测。

Decode（增量生成）：随后每轮产生新的 Token，并继续预测下一步。后面的内容依赖前面刚刚选出的 Token，因此生成轮次有先后顺序。

图 06：左侧 Prefill 处理已有输入；中间用可读片段表现回答逐渐变长；右侧的 KV Cache 是减少重复计算的机制补充，而不是第三个时间阶段。中文片段仅作过程示意。

这不表示 Prefill “只读题”、Decode “才开始计算”。两者都涉及模型计算；区别在于处理的输入形态和工作特点。

每生成一个 Token，都要把历史全部重算吗？

如果每一步都把已经处理过的所有历史内容从头计算一遍，会造成大量重复工作。

因此，很多 Transformer 推理实现会使用 KV Cache：把先前位置在注意力计算中得到的部分中间结果保留下来，供下一轮继续使用。

可以把它理解为：以前已经算过、下一步仍用得上的部分结果，先保存起来。

但缓存不等于“后面不用再经过 Transformer”，更不代表下一段答案已经算好。新的 Token 仍需要参与当前轮的计算，缓存也需要占用内存。

工程上因此会分别关注 TTFT（Time to First Token） 与生成速率。前者衡量请求开始到首个生成结果到达的时间，除了模型处理输入，还受到排队、网络和服务实现等因素影响；后者通常用每秒生成多少 Token 来衡量，关注后续持续生成的速度，不能直接换算成每秒显示多少个汉字。

我们在代码中打开了流式返回，应用就可以逐步接收生成结果并更新界面。但要注意：一次流式返回的数据片段，不保证恰好对应一个 Token；它是 API 交付结果的方式，而不是模型内部计算的精确镜像。

到这里，开头的三个问题基本都能回答了：输入为什么要数字化、回复为什么可能逐步出现、同一问题为什么可能有不同措辞。

回到最初的 API 调用

最开始，我们只是向 API 发送了一句“为什么天空是蓝色的？”，然后在屏幕上看到一段逐渐出现的回答。现在把视线重新放到这次请求上，里面的过程就清晰多了。

服务端先把输入文字转换为 Token ID，再映射成可计算的数值表示；模型结合上下文进行多层计算，为接下来可能出现的 Token 打分，并按解码策略选出一个。新 Token 又成为后续生成的上下文，如此循环，直到回答结束。如果 API 开启了流式返回，已经产生的内容可以在生成期间陆续送到客户端。

我们讨论的是使用现有参数生成文字的推理过程，并不是模型每收到一个问题就重新学习一次。模型参数从何而来、为什么能承载语言规律，属于训练阶段的问题。工具调用也不是普通文本回答的必经步骤；只有应用需要访问外部信息或执行操作时，才会出现模型提出调用意图、应用执行并反馈结果的额外流程。

至此，最初看起来简单的 API 调用，已经能拆成一条从输入到输出的连续信息流。而这条信息流的第一步，还藏着一个值得细看的问题：我们输入的是一句完整的中文，Tokenizer 为什么不一定按一个汉字或一个词来切分？

这不仅关系到模型读入了什么，也直接影响上下文长度的计算方式，以及开发者实际遇到的 Token 用量和成本。
