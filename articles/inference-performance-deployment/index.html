LLM 推理为什么又慢又占显存？从单次生成到在线服务

用可复核的显存与延迟算例理解 TTFT、TPOT、System TPS、显存容量和带宽，并解释 Batching、KV Cache 量化与在线推理服务的资源取舍。

上一篇文章里，我们解决了一个问题：GPT 每生成一个新 Token，不必重新计算整个历史前缀。通过 KV Cache，模型可以复用之前已经算出的 Key 和 Value。

但 KV Cache 解决的是单个请求如何减少重复计算。真正把模型放到服务端之后，还要面对另一个问题：同一张 GPU 可能同时服务很多请求。每个请求有自己的上下文和 KV Cache，长度也不一样；GPU 既要处理新请求，又要继续生成已有请求的 Token。

这时，“模型每秒能生成多少 Token”已经不足以说明服务体验。我们至少要分清三件事：

  • 用户多久能看到第一个 Token，之后的 Token 又隔多久出现？
  • 整个服务每秒能为所有用户生成多少 Token？
  • GPU 能同时容纳多少请求，又能以多快的速度把模型权重和 KV Cache 提供给计算单元？

先给出本篇的核心关系：显存容量决定权重和请求状态能否同时放下；显存带宽决定这些数据能多快被读取；调度决定多个请求怎样共享 GPU。 它们共同影响用户延迟和系统吞吐。

一、一个请求的“快”和整个服务的“快”不是一回事

先沿用 AI05 的单请求场景：用户提交 Prompt，模型经过 Prefill 建立 KV Cache，再进入 Decode，逐步生成回答。

现在把请求数量从一个增加到多个。模型权重通常只需要加载一份，但每个活动请求都有自己的上下文和 KV Cache。并发增加，一方面可能让 GPU 更充分地工作；另一方面也会增加缓存占用，并让请求之间产生排队和资源竞争。

因此，评价在线推理服务时，需要先把“快”拆成不同指标。

先看一条请求：TTFT、TPOT 和 E2E

假设用户在 0 秒提交请求，模型返回了 4 个 Token，时间点如下：

事件 时间
用户提交请求 0.0 s
收到第 1 个 Token 0.2 s
收到第 2 个 Token 0.8 s
收到第 3 个 Token 1.4 s
收到第 4 个 Token 2.0 s

这条时间线可以计算出三个不同的延迟指标。

TTFT（Time To First Token，首 Token 延迟）：从请求提交到第一个 Token 到达的时间。

TTFT=tfirst−tsubmit=0.2−0=0.2 sTTFT = t_{\mathrm{first}} - t_{\mathrm{submit}} = 0.2 - 0 = 0.2\ \mathrm{s}TTFT=tfirst​−tsubmit​=0.2−0=0.2 s

它回答的是：用户发出请求后，要等多久才能看到第一点输出？

这里有一个容易混淆的地方：TTFT 不等于纯粹的 Prefill 计算时间。 从客户端发出请求开始计时，排队、网络传输、输入处理、Prefill，以及首 Token 返回前的处理都可能包含在内。服务端内部的 Benchmark 如果从请求到达服务器时才开始计时，口径又会不同。

TPOT（Time Per Output Token，每个输出 Token 的平均耗时）：第一个 Token 之后，后续 Token 平均隔多久生成一个。

这条时间线有三个 Token 间隔：0.6 s、0.6 s、0.6 s。因此：

TPOT=tlast−tfirstN−1=2.0−0.24−1=0.6 s/tokenTPOT = \frac{t_{\mathrm{last}}-t_{\mathrm{first}}}{N-1} = \frac{2.0-0.2}{4-1} = 0.6\ \mathrm{s/token}TPOT=N−1tlast​−tfirst​​=4−12.0−0.2​=0.6 s/token

TPOT 描述的是 Decode 阶段的输出节奏，不把首 Token 前的等待时间算进去。ITL（Inter-Token Latency）通常指相邻两个 Token 之间的具体时间间隔；TPOT 可以理解为一条请求中这些间隔的平均值。不同 Benchmark 工具对指标名称和统计口径可能略有差异，比较结果前必须先核对定义。

E2E Latency（End-to-End Latency，端到端延迟）：从提交请求到完整响应结束的时间。

E2E=tlast−tsubmit=2.0 sE2E = t_{\mathrm{last}} - t_{\mathrm{submit}} = 2.0\ \mathrm{s}E2E=tlast​−tsubmit​=2.0 s

当输出 Token 数量为 NNN 且 N>1N>1N>1 时，可以写成：

E2E=TTFT+(N−1)×TPOTE2E = TTFT + (N-1)\times TPOTE2E=TTFT+(N−1)×TPOT

三个指标分别回答不同问题：

指标 它衡量什么 用户感受到的是什么
TTFT 请求到首 Token 的等待时间 多久开始有响应
TPOT 后续 Token 的平均间隔 输出是否连贯、是否够快
E2E 从请求到完整响应的总时间 整个任务多久完成

同一条请求时间线：TTFT 测首 Token 前等待，TPOT 测后续输出间隔，E2E 测整条请求耗时；图中数字为教学示例。

如果一个聊天服务 TTFT 很高，用户会觉得“半天没反应”；如果 TPOT 很高，用户可能已经看到了开头，但后面的文字一个字一个字地慢慢出现。只看 E2E，无法区分这两种体验。

再看多个请求：System TPS 不等于单用户速度

现在假设有 3 个请求同时到达。为了让计算简单，先假设它们的输出时间线完全相同：每个请求都在 0.2 s 收到第一个 Token，之后每隔 0.6 s 收到一个 Token，最终在 2.0 s 完成，每个请求共输出 4 个 Token。

单个请求的体验没有变化：

  • TTFT：0.2 s
  • TPOT：0.6 s / Token
  • E2E：2.0 s

但整个服务一共输出了 3×4=123\times4=123×4=12 个 Token。按“第一个请求提交到最后一个响应完成”的统计窗口计算。这里的 System TPS 只统计输出 Token；有些工具还会报告输入与输出合计的 Total TPS，或每秒完成请求数 RPS，不能混为一谈：

System TPS=12 tokens2.0 s=6 tokens/sSystem\ TPS = \frac{12\ \mathrm{tokens}}{2.0\ \mathrm{s}} = 6\ \mathrm{tokens/s}System TPS=2.0 s12 tokens​=6 tokens/s

而单个请求在整个 2 秒内输出 4 个 Token，平均是 2 tokens/s。

这两个数字并不矛盾：

  • System TPS 统计整个服务的总输出速度，多个请求的 Token 都计入分子。
  • Per-user TPS 关注单个请求的输出速度，不能把所有用户生成的 Token 加在一起。

对于很长的输出，单个用户的持续输出速度会逐渐接近 1/TPOT1/TPOT1/TPOT。但对短回答，首 Token 等待占比更高，不能直接把 1/TPOT1/TPOT1/TPOT 当成整条请求的平均速度。

并发增加时，System TPS 通常会先提高，因为 GPU 可以把一次权重读取用于更多请求；达到硬件或调度能力的上限后，吞吐会趋于饱和，继续增加请求可能只会让排队时间和延迟变长。

因此，System TPS 提高，不代表每个用户都变快了。 这也是为什么推理服务不能只公布一个 tokens/s 数字。

二、GPU 显存里到底放着什么？

要理解并发为什么会受到显存限制，先把 GPU 显存中的内容分开。

对于一个正在运行的 LLM，最重要的两类数据是：

  1. 模型权重（Weights）：模型加载后需要持续使用的参数，主要由参数量和每个参数的存储精度决定。
  2. KV Cache：每个活动请求在推理过程中产生的上下文状态，随着 Token 增加而增长。

此外，还需要给临时工作区、运行时缓冲区、CUDA 和推理框架的内存池等留出空间。它们不是模型权重，也不是 KV Cache，但同样会占用显存。

模型权重：加载一次，通常由参数量决定

先看一个假设的 8B 参数模型。这里的 8B 表示约 80 亿个参数。

如果使用 FP16，每个参数占 2 Bytes：

Mweights=8×109×2=16×109 BytesM_{\mathrm{weights}} = 8\times10^9\times2 =16\times10^9\ \mathrm{Bytes}Mweights​=8×109×2=16×109 Bytes

也就是 16 GB。注意 GB 是十进制单位；换成二进制单位约为 14.90 GiB。

这个数字描述的是模型权重本身的理论存储量，不包括运行时开销。它也不代表每个请求都要单独存一份权重：同一份模型权重可以被多个请求共同使用。

KV Cache：每个请求一份，随着上下文增长

KV Cache 不同。每个活动请求都需要保存自己的历史 K 和 V；请求越长，缓存越大。

一个 Token 在每一层都会产生 K 和 V。假设模型有 LLL 层，每层有 HKVH_{KV}HKV​ 个 KV Head，每个 Head 的维度是 DheadD_{\mathrm{head}}Dhead​，每个数值占 SSS Bytes，那么一个请求每增加一个 Token，理论上需要增加：

MKV/token=2×L×HKV×Dhead×SM_{\mathrm{KV/token}} = 2\times L\times H_{KV}\times D_{\mathrm{head}}\times SMKV/token​=2×L×HKV​×Dhead​×S

公式里的 2 表示 K 和 V 各一份；H_KV 是实际保存 K/V 的 Head 数，不是 Query Head 数。这个估算适用于常见的标准 Attention KV Cache 结构，忽略块分配余量和元数据；滑动窗口、MLA 等特殊结构可能改变实际缓存量。

如果同时有 BBB 个请求，每个请求缓存的 Token 数量分别是 T1,T2,…,TBT_1,T_2,\ldots,T_BT1​,T2​,…,TB​，那么总 KV Cache 容量为：

MKV=2×L×HKV×Dhead×S×∑i=1BTiM_{\mathrm{KV}} =2\times L\times H_{KV}\times D_{\mathrm{head}}\times S \times\sum_{i=1}^{B}T_iMKV​=2×L×HKV​×Dhead​×S×i=1∑B​Ti​

如果所有请求长度相同，才可以简化为 B×TB\times TB×T。真实服务中的请求长度往往不同，所以更准确的计算方式是把每个请求实际缓存的 Token 数相加，而不是一律按最大上下文长度估算。

继续使用一个固定教学算例：

  • 模型有 32 层。
  • 每层有 8 个 KV Head。
  • 每个 Head 的维度是 128。
  • K 和 V 都使用 FP16，每个数值占 2 Bytes。

代入后：

2×32×8×128×2=131072 Bytes=128 KiB2\times32\times8\times128\times2 =131072\ \mathrm{Bytes} =128\ \mathrm{KiB}2×32×8×128×2=131072 Bytes=128 KiB

也就是说，每个请求每增加一个缓存 Token，约增加 128 KiB 的 KV Cache。

当单个请求的上下文达到 8192 Tokens：

128 KiB×8192=1 GiB128\ \mathrm{KiB}\times8192=1\ \mathrm{GiB}128 KiB×8192=1 GiB

如果 8 个请求都达到 8192 Tokens：

1 GiB×8=8 GiB1\ \mathrm{GiB}\times8=8\ \mathrm{GiB}1 GiB×8=8 GiB

把模型权重和 KV Cache 放在一起：

显存项目 理论占用
8B 模型权重，FP16 14.90 GiB
8 个请求的 KV Cache 8.00 GiB
合计 22.90 GiB

假设 GPU 总容量是 24 GiB，那么这两项相加后只剩约 1.10 GiB，还没有计算临时工作区、运行时缓冲区和内存分配预留。实际部署时，这点空间很可能不够。

这就解释了一个现象：模型权重能够加载进 GPU，不代表它就能承载足够多的并发请求。 权重是相对固定的占用；KV Cache 则会随活动请求数量和上下文长度变化。

8B FP16 模型的权重占用相对固定，活动请求各自增长的 KV Cache 会挤占剩余显存；运行时工作区尚未计入。

还要记住，公式里的 TiT_iTi​ 包含当前请求已经进入上下文的 Token，不只是用户最初输入的 Prompt。Decode 每生成一个新 Token，缓存就会继续增长，直到请求完成并释放或回收对应的缓存资源。

三、显存容量够了，为什么推理仍然可能很慢？

到这里，我们知道模型权重和 KV Cache 要占用多少空间。但还有一个容易忽略的问题：

数据已经放进 GPU 显存，不等于 GPU 计算单元可以不花时间地使用它们。

GPU 计算时，需要把数据从显存搬运到计算单元附近。这里有两个完全不同的指标：

  • GPU Memory Capacity（显存容量）：总共能放下多少数据，单位通常是 GB 或 GiB。
  • Memory Bandwidth（显存带宽）：每秒能够搬运多少数据，单位通常是 GB/s 或 TB/s。

可以把它们理解为两个不同的问题：容量决定仓库能装多少货，带宽决定每秒能从仓库运出多少货。仓库很大，不代表运输速度就很快。

维度 显存容量 显存带宽
衡量什么 能同时容纳多少数据 每秒能读取或写入多少数据
典型限制 权重和 KV Cache 放不下，并发受限 数据放得下，但计算单元等待数据
主要影响因素 参数量、精度、上下文长度、并发数 每轮读取的数据量、精度、Batch 复用程度、硬件带宽

为什么 Decode 特别容易受到显存带宽限制？

继续使用刚才的 8B FP16 模型。权重有 16 GB。

在 Decode 阶段，每一轮都要根据当前 Token 计算下一 Token。模型的权重需要参与这一轮计算。由于模型权重远大于 GPU 片上缓存，粗略估算时，可以把每轮从显存读取一遍权重作为一个简化假设。

如果这一轮只服务一个请求，那么这次权重读取只产出一个新 Token：

16 GB1 Token=16 GB/Token\frac{16\ \mathrm{GB}}{1\ \mathrm{Token}} =16\ \mathrm{GB/Token}1 Token16 GB​=16 GB/Token

如果这一轮同时处理 8 个请求，需要注意：这 8 个请求的输入表示并不相同，但它们经过的是同一套模型权重。

以某一层的线性变换为例。假设 8 个请求在这一层各自有一个不同的隐藏状态向量：

y1=Wx1,y2=Wx2,…,y8=Wx8y_1=Wx_1,\quad y_2=Wx_2,\quad \ldots,\quad y_8=Wx_8y1​=Wx1​,y2​=Wx2​,…,y8​=Wx8​

这里的 W 是模型中所有请求共用的权重矩阵；矩阵右侧的 8 个输入向量分别来自不同请求，彼此并不相同。把它们组织成一个矩阵，就可以合并为一次批量矩阵运算：

Y=W[x1,x2,…,x8]Y=W[x_1,x_2,\ldots,x_8]Y=W[x1​,x2​,…,x8​]

它表达的仍然是 8 次各自独立的计算，只是 GPU 可以把它们组织成更适合并行硬件的矩阵运算。计算过程中，GPU 将权重分块搬到片上存储，让同一块权重参与多个请求的计算，而不必为每个请求都从显存重新搬运一遍相同的数据。

因此，前面的“读取一次权重”是一个理想化的权重流量模型：假设一轮 Decode 中约读取 16 GB 权重，并让这批权重服务 8 个请求。这不是说真实 GPU 一定只从显存读取恰好一次完整的 16 GB；实际流量还会受到矩阵分块、缓存命中、Kernel 实现等因素影响。

在这个简化模型中，这一轮会产出 8 个 Token：

16 GB8 Tokens=2 GB/Token\frac{16\ \mathrm{GB}}{8\ \mathrm{Tokens}} =2\ \mathrm{GB/Token}8 Tokens16 GB​=2 GB/Token

这就是 Batch 能提高系统吞吐的一个重要原因：不同请求使用各自的输入和状态，但可以复用同一套模型权重；权重搬运成本由更多输出 Token 分摊。

再假设显存带宽为 2 TB/s，只计算这 16 GB 权重的读取时间：

16 GB2 TB/s=8 ms\frac{16\ \mathrm{GB}}{2\ \mathrm{TB/s}} =8\ \mathrm{ms}2 TB/s16 GB​=8 ms

这 8 ms 是一个理想化的权重读取下界，不是实际 GPU 测试结果。它没有计算 KV Cache 的读取、矩阵运算、Kernel 调度和其他运行时开销。

但它足以帮助我们理解 Batch 的作用：

  • Batch = 1：一轮约读取 16 GB 权重，产出 1 个 Token。
  • Batch = 8：在理想化估算中，一轮约读取 16 GB 权重，供 8 个不同请求各自计算一个 Token；真实显存流量取决于 Kernel 分块与缓存行为。

在这个极简模型里，Batch = 8 可以显著提高 System TPS；但每个请求仍然要等这一轮完成，才能收到自己的下一个 Token。系统每轮产出更多 Token，不等于单个用户的 TPOT 自动缩短为原来的八分之一。

真实 Decode 还要读取 KV Cache。每个新 Token 的 Query 需要访问历史 K/V；上下文越长，需要访问的历史数据通常越多。因此，KV Cache 不仅占用显存容量，也会带来持续的显存带宽压力。

为什么 Prefill 和 Decode 的资源瓶颈不同？

这也解释了为什么 Prefill 和 Decode 虽然属于同一次推理，却常常呈现不同的性能特征。

Prefill 一次处理一段已经确定的 Prompt。 比如输入有 8192 个 Token，这些位置都已经存在，可以一起参与矩阵运算。大量 Token 同时参与计算，矩阵规模较大，GPU 的计算单元更容易被充分利用。因此，Prefill 在很多常见场景下更偏向计算密集型（Compute-bound）。

Decode 每轮只为每个活动请求处理一个新 Token。 如果 Batch 很小，GPU 每轮仍要读取大量模型权重，但只产出少量 Token，数据搬运相对于计算的比例较高，所以常见瓶颈是显存带宽（Memory-bandwidth-bound）。

当 Batch 增大时，不同请求仍使用各自的隐藏状态和 KV Cache，但它们可以复用同一套权重数据；Decode 的权重复用率提高，瓶颈也可能逐渐转向计算能力。实际情况还取决于模型结构、上下文长度、GPU、Kernel 和推理框架，不能把“Prefill 一定计算密集、Decode 一定带宽受限”当成固定定律。

这两种阶段的差异会影响服务调度：长 Prompt 的 Prefill 可能占用大量计算资源，打断或延迟其他请求的 Decode；如果用户正在等待连续输出，这种干扰就会反映到 TPOT 上。DistServe 的研究正是从 Prefill 和 Decode 的资源差异与相互干扰出发，探索将两个阶段分配到不同 GPU 的方案。这样做可以独立优化两种延迟，但也需要传输 KV Cache，并增加系统复杂度。

四、多个请求怎样共享 GPU？Batching 解决什么问题？

现在把前面几件事放在一起：

  • Batch 太小：GPU 可能没有充分利用计算资源，权重读取难以被多个请求共同摊薄。
  • Batch 变大：权重复用更充分，System TPS 通常会上升。
  • 但活动请求变多：KV Cache 占用也会增加。
  • 如果 GPU 已经饱和：继续增加请求，可能只增加排队时间和延迟。

因此，服务端需要一个调度机制，决定当前这一轮让哪些请求一起执行。

Batch 和并发请求不是同一个数字

**Concurrency（并发请求数）**描述同一时间有多少请求处于服务过程中；Batch Size描述某一轮模型执行中，实际一起参与计算的请求数量。

例如，系统里可能有 20 个请求正在等待或执行，但由于显存和调度限制，当前这一轮只能安排其中 8 个请求一起计算。此时并发请求数是 20，当前 Batch Size 是 8。剩余请求需要等待后续资源空出来。

Continuous Batching：不必等整批请求全部结束

一种简单的固定 Batch 做法，是先凑齐一批请求，再一起执行。问题在于，不同请求的输入和输出长度不同：有的请求很快完成，有的还需要生成很多 Token。如果必须等待整批结束，已经完成的请求位置可能被浪费；如果为了对齐长度而填充，也会产生无效计算。

Continuous Batching（连续批处理，也称 In-flight Batching）采用了更灵活的方式：

  1. 当前 Batch 中的请求执行一轮模型计算。
  2. 已经生成结束的请求退出。
  3. 等待中的新请求在资源允许时加入。
  4. 下一轮重新组织当前参与计算的请求。

它不是等所有请求都结束后再组成下一批，而是在生成过程的迭代边界动态调整 Batch 成员。这样可以减少空闲位置，更充分地利用 GPU。

左侧固定 Batch 留下空位直到整批结束；右侧在迭代边界移出已完成请求，待新请求完成 Prefill 且资源允许时补入。

不过，Continuous Batching 并不意味着请求永远不会排队，也不保证 TTFT 和 TPOT 同时下降。GPU 资源达到上限后，新请求仍要等待；如果长 Prompt 的 Prefill 与已有请求的 Decode 争用资源，后续 Token 的间隔也可能变长。具体调度策略和参数因推理引擎而异，可以参考 TensorRT-LLM 对 In-flight Batching 和请求调度的说明。

KV Cache 为什么还需要专门的内存管理？

前面算过，一个 8192 Token 的请求需要约 1 GiB KV Cache。实际服务中的请求长度不同，而且缓存会随着生成逐步增长。

如果为每个请求都预留一块足够容纳最大上下文的连续内存，短请求会浪费大量空间；请求结束、缓存释放后，还可能形成难以利用的内存碎片。即使 GPU 总空闲显存看起来不少，也可能找不到合适的连续空间来满足新的分配。

PagedAttention 的思路，是把请求的 KV Cache 按固定大小的 Block 管理。请求需要更多缓存时，再分配新的 Block；这些 Block 不必在显存中连续排列。这样可以减少连续内存分配带来的浪费和碎片，让推理引擎更灵活地安排不同长度的请求。

这里要分清：PagedAttention 改善的是 KV Cache 的分配和管理效率，不会让一个请求真实需要保存的 K/V 数据凭空消失。 8 个请求、每个 8192 Token 的理论缓存数据仍然约为 8 GiB。PagedAttention 的价值在于减少额外浪费，让更多有效缓存能够被放进同一块 GPU 显存。

五、资源不够时，应该优化哪一部分？

现在可以根据瓶颈来理解几种常见优化，而不是把它们当作互不相关的技术名词。

当前瓶颈 优化思路 它改变了什么 需要付出的代价
KV Cache 分配浪费、碎片较多 Block-based KV Cache / PagedAttention 减少分配浪费，让缓存按需增长 增加块管理和映射逻辑；真实 K/V 数据仍然存在
模型权重占用或读取量太大 权重量化 用更低精度存储权重，减少权重容量和搬运量 可能引入数值误差；需要硬件和 Kernel 支持
KV Cache 占用或读取量太大 KV Cache 量化 降低每个缓存元素的存储字节数 可能影响注意力计算和生成质量
Prefill 与 Decode 互相干扰 Prefill / Decode 分离 让两个阶段使用不同的 GPU 资源 需要传输 KV Cache，并增加部署和调度复杂度

KV Cache 量化：压缩的是每个请求的上下文状态

前面计算 KV Cache 时，公式中的 SSS 表示每个 K/V 数值占用的字节数。我们的算例使用 FP16，所以 S=2S=2S=2，每个 Token、每个请求需要 128 KiB。

如果把 KV Cache 改为 FP8 存储，每个数值的原始存储空间就从 2 Bytes 降到 1 Byte。其他模型结构和上下文长度不变时，KV Cache 的原始数据量理论上减半：

场景 FP16 KV Cache FP8 KV Cache
每个请求，每 Token 128 KiB 64 KiB
单请求，8,192 Tokens 1 GiB 0.5 GiB
8 个请求，各 8,192 Tokens 8 GiB 4 GiB

这就是 KV Cache 量化的直接价值：同样的 GPU 显存可以容纳更多请求或更长的上下文；读取历史 K/V 时，需要搬运的数据量也有机会减少。

它是怎么做到的？K 和 V 原本是浮点数。量化会用更低精度的格式表示这些数值，例如把 FP16 值映射为 FP8，同时保存配套的缩放信息（scale），让运行时能够按相应规则处理这些近似值。不同推理引擎可能采用不同的缩放粒度和 Attention Kernel；有的实现会在读取时进行反量化，有的则支持直接使用低精度 KV 参与计算。NVIDIA TensorRT-LLM 就提供了 FP8 KV Cache 选项，并在其 Attention 实现中处理相应的缩放与数值转换。

当然，FP8 并不是把每个 FP16 数值简单截掉一半字节就结束了。低精度表示会引入量化误差，可能影响注意力计算和最终生成质量；缩放信息、块对齐和运行时工作区也会带来额外开销。因此，表中的减半是KV 数值本身的理论存储量，不是实际 GPU 显存必然减少一半，更不代表推理速度一定提高一倍。是否值得启用，需要在目标模型、上下文长度和真实请求分布下验证质量与吞吐。

它与 PagedAttention 解决的问题也不同：PagedAttention 改善 KV Cache 的分配方式，减少连续内存分配和碎片浪费；KV Cache 量化则减少每个 K/V 数值本身占用的字节数。两者可以互补，但都不能让请求的历史状态凭空消失。

权重量化：压缩的是模型参数

权重量化处理的是另一份数据：模型本身的参数。以 8B 模型为例，如果只看原始数据存储量，FP16 权重约为 16 GB，改为 FP8 后理论上约为 8 GB。它主要减少模型权重的显存占用和读取量；KV Cache 量化减少的则是请求级动态状态。

两类量化都可能引入数值误差，也都依赖硬件和高效 Kernel 的支持。实际收益不能只根据每个数值占几个字节判断，还要测量模型质量、显存峰值、TTFT、TPOT 和 System TPS。

所以，优化之前要先判断当前卡在哪里：

  • 权重和 KV Cache 放不下：优先考虑容量管理、缓存分配和精度。
  • 数据放得下，但 Decode 仍然慢：检查显存带宽、权重复用、KV Cache 读取和 Kernel 效率。
  • 首 Token 等待或后续 Token 间隔变差：检查排队、Batch 调度，以及 Prefill 对 Decode 的干扰。

没有一种优化能同时解决所有瓶颈。把容量问题当成带宽问题处理，或者只提高 Batch 却不考虑 KV Cache 占用，都可能得不到预期结果。

六、怎样判断一个推理服务真的变快了？

最后回到最初的问题：怎样评价一个在线推理服务？

至少需要同时观察：

指标 关注点
TTFT p50 / p95 一般请求和较慢请求分别要等多久才看到首 Token
TPOT / ITL p50 / p95 后续 Token 的输出节奏是否稳定
E2E p50 / p95 完整请求需要多久
System TPS 整个服务每秒实际输出多少 Token
GPU Memory Peak 权重、KV Cache 和运行时的显存峰值
成功率、超时率 吞吐提高时，服务是否仍然可靠

为什么要看 p50 和 p95？因为平均值可能掩盖少量特别慢的请求。p95 表示 95% 的请求指标不超过这个值，剩余 5% 更慢。比如大部分用户 1 秒内就看到首 Token，但有 5% 的请求要等 8 秒，平均值可能看起来还可以，真实体验却已经受到影响。

测试时也不能只改一个 Batch 参数，然后比较两次输出的 TPS。至少需要固定或记录：

  • 模型版本、权重精度和推理引擎版本。
  • GPU 型号及数量。
  • Prompt 长度和输出长度的分布。
  • 并发请求数、请求到达速率和最大 Batch 配置。
  • 预热方式、测试时长和采样参数。

还要区分两类测试：

  • Performance Benchmark（性能基准测试）：尽量测清模型和推理引擎在特定配置下的处理效率。
  • Load Test（负载测试）：模拟真实请求持续到达，观察排队、容量、延迟、成功率和资源利用率。

前者告诉我们模型和引擎本身处理得有多快，后者告诉我们服务在目标流量下能否稳定运行。两者结合，才能判断一次优化是否真的有价值。

回到最初的问题

LLM 推理之所以又慢又占显存，不是一个孤立的“模型太大”问题，而是几个因素共同作用：

  • TTFT 决定用户要等多久才能看到第一个 Token。
  • TPOT 决定后续 Token 输出得有多快。
  • System TPS 衡量所有请求加在一起的总输出能力。
  • GPU Memory Capacity 限制模型权重和活动请求的 KV Cache 能否同时放下。
  • Memory Bandwidth 限制每一轮 Decode 能多快读取权重和历史 K/V。
  • Batching 和调度 则在单用户延迟、系统吞吐和显存容量之间做取舍。

KV Cache 让模型少做重复计算，但也带来了持续增长的请求状态；Batching 让不同请求的计算能够复用同一套权重，却会增加活动 KV Cache 的总量；显存容量和带宽又限制了这些请求能以多大规模、怎样的速度运行。

在线推理服务真正要优化的，不是某一个孤立的 tokens/s 数字，而是在目标延迟和资源预算内，稳定地服务尽可能多的请求。

到这里，我们已经从模型内部的逐 Token 生成，走到了模型如何作为在线服务运行。接下来还有一个不同层面的问题：模型为什么能处理训练时没有直接见过的表达？如果希望它表现出新的能力，又应该怎样改变它？

按照已经确定的路线，AI06 完成后会另开「模型学习与能力适配」专题，先研究泛化，再研究微调。它们不属于本篇推理性能与部署的范围。
